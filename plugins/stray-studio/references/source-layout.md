# Source Layout

Use this shared reference before creating or moving source files, reusable scripts, or repository-managed configuration. For reviews, apply it to the affected placement decisions while preserving the calling skill's review-only boundary. Keep framework, tool, and language semantics ahead of cosmetic uniformity.

## Workflow

1. Identify the framework's required paths, reserved names, generators, language package semantics, and repository placement rules before choosing a destination. Follow framework requirements first, then compatible repository conventions. Use the framework's recommended structure as the starting point for a new app. Keep required routing, migration, generated-code, and test-discovery layouts; organize only where they leave freedom.
2. Choose the existing directory that owns the behavior. Within freely organized areas, group by feature or responsibility and by what changes together. Keep implementation, focused tests, fixtures, and feature-owned prompts nearby where conventions allow; otherwise use corresponding directories in the required test or asset layout. Keep framework-defined layers when required or established; organize within them rather than replacing the app's structure.
3. Establish the smallest responsibility-based folder structure before writing the first files; do not wait for files or classification prefixes to accumulate. Reuse an appropriate owning directory, or create a responsibility-named directory when the requested behavior needs a distinct home. Base the grouping on shared responsibility and actual use; matching prefixes alone are insufficient. Keep a small coherent directory flat. Do not impose file-count limits, a fixed depth, a folder per file, or mandatory `features/` nesting.
4. Prohibit repeated feature or category prefixes used merely to group files in a flat directory unless there is a concrete technical or domain reason. For example, use `reservations/validation.ts` and `reservations/pricing.ts` instead of source-root `reservation_validation.ts` and `reservation_pricing.ts` when placement is free. Alphabetical grouping or existing prefix usage alone is not a sufficient reason. Allow required framework/tool names such as `test_*.py`, meaningful names describing the actual contents such as `UserProfile.tsx`, and prefixes needed to preserve language package semantics or a public compatibility contract. State the reason for an exception in the change description or existing guidance. Preserve required suffixes and package boundaries; do not rename descriptive files or reorganize unrelated code just to remove a repeated word.
5. Keep code local to its owner until actual consumers need the same meaning and reasons for change. Extract shared code under a concrete responsibility such as date formatting or HTTP transport; do not use a generic `utils/`, `helpers/`, or `common/` directory as the default destination for new code. Reuse an appropriate existing shared module and add internal layers only when the responsibilities need separation.
6. Limit moves to the requested change and the affected grouping; do not reorganize unrelated code for visual consistency. For moved files, update imports, public exports, registrations, path-based configuration, test discovery, fixtures, and asset or prompt references as applicable. Run affected consumer and build/test checks. Describe a non-obvious placement decision in the existing guidance or change description; do not create a new architecture document for routine additions.

## Validation Cases

Use these synthetic cases to check the placement decision; they do not demonstrate agent runtime compliance.

| Case | Expected decision | Failure |
|---|---|---|
| Framework prescribes route files and layer directories | Preserve those paths and names; group within the areas it leaves free | Replace the prescribed layout with a universal feature tree |
| New app needs reservation and inventory logic in a freely organized source area | Choose the smallest responsibility-based directories before writing the first files, with related tests or corresponding test paths | Start with classification-prefixed files at the source root and defer grouping until more files exist |
| Existing directory uses category prefixes but new code has no technical or domain reason to do so | Place the new code under its responsibility without an unrelated bulk move | Treat existing prefix usage or alphabetical grouping as sufficient justification |
| Test discovery requires `test_` and a component's contents are accurately named `UserProfile.tsx` | Preserve the required test prefix and descriptive component name; explain the applicable reason | Apply a blanket word-prefix ban or invent a folder solely to shorten a descriptive name |
| Small Go package contains cohesive files with required test suffixes | Keep the package coherent and flat unless a responsibility needs a separate package | Create subpackages merely to remove repeated filename words |
| Feature needs a private parser while an existing shared module owns HTTP transport | Keep the parser local and reuse the transport module | Create a generic shared bucket or a duplicate transport wrapper |
| Scoped move affects a public export and a fixture path | Update both consumers and run relevant checks | Treat the move as complete after changing imports alone |
| Terraform module contains conventional files; a Helm chart has prescribed paths | Preserve module/state semantics and chart paths; organize only within the tool's available freedom | Create modules or change resource addresses merely to put files in folders |
| CLI scaffold generates entry points and manifest file references | Preserve generator contracts and update affected references when a scoped move is justified | Treat generated filenames as unexplained prefixes or break manifest paths |
