# Kubernetes Repository Changes

Read this reference when the requested repository change or review involves Kubernetes manifests, Helm charts, or Kustomize overlays. Keep standalone infrastructure with `iac-builder`, supporting app infrastructure with `fullstack-app-builder`, and findings with the selected reviewer. Use the [IaC baseline](iac-baseline.md), [lifecycle](iac-lifecycle.md), and [operations](iac-operations.md) for common controls; select only relevant sections below. This reference does not introduce Kubernetes into other runtimes or expand a task into live incident response, cluster administration, or deployment.

## Established Practices And Their Evidence

Distinguish measured adoption, official recommendations, and project decisions. The [2025 CNCF Annual Survey](https://www.cncf.io/wp-content/uploads/2026/01/CNCF_Annual_Survey_Report_final.pdf), Figure 19 (p. 18), reports production use of Helm 81%, Prometheus 77%, cert-manager 58%, Argo 52%, and Flux 23% among respondents to that question (Q32, sample size 395-596, don't-know/not-sure excluded). These are adoption signals within the survey, not market shares or mandatory dependencies; the Argo figure covers the project, not exclusively Argo CD. Official recommendations below are a separate basis and do not prove adoption.

| Concern | Established option or convention | Apply it to the repository |
|---|---|---|
| Packaging and overlays | Helm has strong survey adoption; [Kustomize is supported by kubectl](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/) | Reuse the existing choice. For charts, inspect locked dependencies, values precedence and `values.schema.json` where present; render affected environment inputs. For overlays, keep the shared base and environment patches authoritative. Do not wrap simple manifests in a chart merely to follow a trend. |
| Continuous delivery | [OpenGitOps](https://opengitops.dev/) defines declarative, versioned/immutable desired state, automatic pull and continuous reconciliation; Argo CD and Flux implement this approach | Trace the watched source and revision, synchronization, drift correction, pruning and recovery. Git storage alone is not GitOps. Keep supported existing CI-driven delivery when that is the accepted design. |
| North-south traffic | [Kubernetes recommends Gateway API for new work; Ingress is frozen but remains supported](https://kubernetes.io/docs/concepts/services-networking/ingress/) | Prefer Gateway API for a new design when the platform supports required features. Check version/profile/Route-specific [implementation conformance](https://gateway-api.sigs.k8s.io/docs/implementations/list/); no single controller is mandated. Existing maintained Ingress deployments need an explicit migration case, not an incidental rewrite. |
| Metrics and alerts | Prometheus has strong survey adoption; the [Prometheus Operator](https://prometheus-operator.dev/docs/api-reference/api/) supplies declarative monitor/rule resources when installed | Reuse the existing Prometheus-compatible or managed platform. A ServiceMonitor is an extension, not a built-in Kubernetes API, and its presence does not prove discovery, scraping or notification. |
| Certificate lifecycle | [cert-manager](https://cert-manager.io/docs/usage/certificate/) is an established option; a managed gateway may own certificates instead | Identify the existing issuer/renewal owner and preserve one authority. If using cert-manager, trace Certificate, Issuer/ClusterIssuer, Secret, validation method and consumer; do not install it alongside working managed certificate automation without a need. |
| Workload conventions | Kubernetes recommends [common application labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/), [reproducible image identity](https://kubernetes.io/docs/concepts/containers/images/), and [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) | Reuse `app.kubernetes.io/*` labels where applicable, keep selectors stable, pin production image content by digest where required for reproducibility, and plan updates. Choose an applicable Pod Security profile with explicit workload exceptions instead of a universal copied manifest. |

## Establish The Target And Source Of Truth

1. Inspect the repository's manifests, chart dependencies/lockfiles, overlays, CI and deployment configuration, and affected app consumers. Identify the intended cluster/context, namespace, environment, Kubernetes API versions, pinned kubectl/Helm/Kustomize versions, and platform owner from non-secret configuration. Mark missing facts as unknown; do not connect just to fill them in.
2. Identify who reconciles each resource: plain manifests, Helm, a GitOps controller, Terraform, or an operator. Edit the authoritative input rather than generated output or a controller-owned resource. Preserve release names, selectors, field ownership, and environment overlays; do not add a second reconciler or force ownership conflicts away.
3. Check supported APIs, removed/deprecated versions, CRDs and controller prerequisites against the target versions. Distinguish built-in APIs from installed extensions; declaring a custom resource does not install its controller. Record bootstrap order and its owner when external to the repository.
4. Discover existing tools through repository scripts and PATH. Reuse pinned dependencies; if unavailable, complete static inspection and report the missing check. Do not install a cluster, controller, chart repository, or replacement toolchain merely to validate documentation or configuration.
5. For GitOps, inspect automated synchronization, prune/delete policy, hooks/dependency ordering and drift correction before proposing delivery. [Argo CD uses Helm to render templates and owns the application lifecycle](https://argo-cd.readthedocs.io/en/stable/user-guide/helm/); do not assume a separately managed Helm release. Read the target's [Argo CD sync policy](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/) or [Flux reconciliation/deletion policy](https://fluxcd.io/flux/components/kustomize/kustomizations/). Push or merge to a watched source can deploy or delete resources without a subsequent CLI apply. For a no-deploy request, keep work outside automatically reconciled sources unless their effects are authorized; do not silently disable reconciliation to work around that boundary.

## Select The Affected Contracts

1. **Workload and configuration.** Match long-running replicas, stable identity/storage, per-node agents, or finite/scheduled work to the existing Deployment, StatefulSet, DaemonSet, Job, or CronJob model. Check labels/selectors, image identity, command/ports, config and Secret references, and namespace scope in the rendered output. For jobs, retain app idempotency, bounded retries and overlapping-run policy. Trace how config changes reach running processes; do not assume environment variables or application caches reload automatically.
2. **Health and rollout.** Reuse real app endpoints and startup budgets. Distinguish startup, readiness, and liveness; a downstream outage must not become an unnecessary restart loop. Align termination grace, pre-stop work, request/job draining, and ingress/controller behavior. Review Deployment surge/unavailability, replica capacity, placement and rollback compatibility. A PodDisruptionBudget constrains supported voluntary evictions; it does not govern a Deployment's rolling-update strategy or guarantee availability against every disruption. Image rollback does not undo schema changes or lost data.
3. **Capacity.** Check resource requests/limits against scheduling, memory failure and CPU throttling risks. For HPA, verify the metric source and any required resource requests, then relate minimum/maximum replicas and rollout overlap to node capacity, quotas, DB pools, and downstream limits. Do not treat HPA as node provisioning or a hard spending cap. Keep availability/cost exceptions appropriate to the environment; do not require autoscaling or multi-zone placement for every workload.
4. **Traffic.** Trace client to Service selector/target port, ready endpoints, DNS, ingress or Gateway implementation, TLS, and backend. Check the chosen controller's maintenance status before preserving it. Community `kubernetes/ingress-nginx` retired in March 2026 and its [repository was archived on 2026-03-24](https://github.com/kubernetes/ingress-nginx); do not recommend it for new deployment. Identify the exact implementation rather than conflating every NGINX product or the Ingress API with this retirement. For affected existing installations, report the support gap and scope a migration preserving annotations, rewrites, authentication, timeouts, TLS and client behavior; do not silently swap controllers. An Ingress or Gateway object alone does not establish a working controller, certificate, load balancer, or public endpoint. For NetworkPolicy, inspect selected pods/namespaces, ingress and egress, required DNS/external paths, and additive rules. Confirm the CNI supports enforcement before claiming isolation; namespace separation and YAML presence alone are insufficient.
5. **Persistent data.** Trace PVCs to StorageClass/CSI capabilities, access modes, topology/binding, capacity and reclaim policy. Check what replacement, chart removal, PVC deletion, and retention settings do to actual data. A StatefulSet or retained volume is not a backup; reuse the recovery requirements and name restore evidence separately. Do not change storage ownership or deletion behavior as incidental cleanup.
6. **Identity and security.** Separate deployer, controller and workload identities; inspect namespaced versus cluster-wide RBAC, indirect privilege through workload creation, and service-account token needs. Review Pod Security admission mode/version and runtime security context against workload requirements. Use the existing [infrastructure/container checks](../skills/security-preflight/references/infra-containers.md) for the common security checklist without changing the caller's review/implementation mode. Keep Secret values out of Git, rendered logs and diffs; base64 is not encryption. Distinguish declared policy from effective admission, encryption, access and network enforcement. A security-only review selects these relevant controls, not a general cost/performance audit.
7. **Observability and certificates.** Reuse the [operations guidance](iac-operations.md) for symptoms, retention and response ownership. When Prometheus Operator is present, trace Prometheus namespace/label selectors to ServiceMonitor/PodMonitor, selected Service/Pods and named metrics ports; inspect PrometheusRule selection and Alertmanager routing separately. Check synthetic rule tests where already supported; a discovered target is not proof of an alert reaching its owner. For certificates, distinguish a declared Certificate from issuance, renewal, Secret delivery and the certificate actually served by the endpoint; report unexecuted expiry/renewal checks. Do not send test notifications or issue real certificates solely to validate repository definitions.

## Validate Without Inflating The Evidence

1. Select checks for the changed contract and intended overlay/values. Use synthetic secrets and existing repository checks. Inspect remote bases, chart dependencies, render plugins, post-renderers and credential helpers before execution; a familiar command name is not proof of local-only behavior.

   | Check | What it establishes and what remains unverified |
   |---|---|
   | Local YAML/schema checks using pinned schemas | Syntax and supported fields covered by those schemas; record target Kubernetes/CRD versions and missing schema coverage |
   | `helm lint` / `helm template` with local dependencies and synthetic values | Chart checks and rendered objects; no proof of server API support, admission, scheduling or successful hooks |
   | `kubectl kustomize` / existing Kustomize build with local inputs | Rendered overlay, names, selectors, references and environment separation; no proof of effective cluster behavior |
   | `kubectl apply --dry-run=server` | Sends objects to the API server for authorization, defaulting and admission without persisting the requested objects; requires authorized cluster access and does not run the workload |
   | `kubectl diff` | Contacts the API server and compares live versus proposed objects; may reveal sensitive values and invokes a diff program; differences (exit 1) are distinct from errors (exit greater than 1) |

   If the repository uses [kubeconform](https://github.com/yannh/kubeconform), select the target Kubernetes version, strict validation and local pinned schema locations for offline checks. Its default schema lookup downloads from the network. Supply relevant CRD schemas or report uncovered resources; `-ignore-missing-schemas` must not turn skipped custom resources into a claim that all objects passed. This is a tool option, not an adoption claim or a required new dependency. Likewise, schema validation does not replace the project's existing admission/policy tests.

2. Do not call `kubectl apply --dry-run=client` universally offline: discovery or validation can require API access depending on command/version. For a no-cluster task, use verified local rendering/schema paths. Helm dry-run modes are also version-dependent; inspect the actual command rather than assuming every dry-run is local.
3. Before authorized API access, confirm the context, namespace, server destination and identity without dumping kubeconfig or tokens. Account for kubeconfig exec authentication and the data sent to the API/admission chain. Reuse authorization already covering the target/effect; source editing alone does not authorize access, apply, install/upgrade, hooks/jobs, rollout restart, eviction, deletion, or paid resources. Review-only skills retain their restrictions on active checks.
4. For authorized deployments, use the established delivery path and capture sanitized admission, rollout, scheduling/image-pull, readiness and application evidence. Verify only the changed contracts, including effective access or restoration when those claims are required. If a result is ambiguous, inspect the authorized target before retrying; do not force conflicts, delete resources, or perform an unapproved rollback to hide partial success.
5. Hand off the authoritative files and target assumptions, rendered/static results, missing dependencies, and unexecuted live checks. Keep declared, rendered, server-accepted, deployed and runtime-verified states distinct. No new report file or cluster is required solely to fill these statuses.
