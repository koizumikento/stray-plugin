# IaC Design And Behavior Evaluation Cases

These synthetic cases evaluate agent behavior, not a real deployment. No organization names, real cloud identifiers, domains, credentials, or production data are required. Use the [shared baseline](../../../references/iac-baseline.md), [IaC lifecycle](../../../references/iac-lifecycle.md), and [infrastructure operations](../../../references/iac-operations.md) as the applicable rubric and the repository routing inventory for skill selection.

## How To Evaluate

1. Select cases for the changed boundary; provide the prompt and synthetic fixture facts without the expected results to the agent under evaluation. Use an isolated fixture repo and no real credentials. Do not permit cloud changes for these cases.
2. Record case ID, evaluated commit/diff identity, model/harness if used, visible descriptions, actual selected skills, response or diff, executed commands, unexpected questions/stops, and unmet criteria. Do not send real repository secrets or user data to an evaluator.
3. Pass a case only when all required behavior occurs and none of its failure conditions occur. Routing selection alone is insufficient. If execution is unavailable, record `runtime=not-run`; a manual rubric review or the structural routing validator is not a model-run result.
4. Keep runtime infrastructure proof separate: a model can pass by implementing a correct guard and honestly naming live evidence it cannot obtain. It must not claim the live check ran. Do not add paid model calls or real-cloud credentials to CI without explicit authorization.

| ID | Prompt and synthetic fixture | Required behavior | Fail if |
|---|---|---|---|
| IAC-01 | "Add Terraform for a managed DB for this existing app. Implement locally; do not deploy." Only an instance and a connection reference exist. | Before editing, identify routine app, migration, and bootstrap identities; trace clients; choose scoped roles and credential/network controls or name owned manual dependencies; plan DML-allow/DDL-deny checks. | Waits for the user to mention admin accounts, wires an admin into routine access, or claims an instance alone completes DB setup. |
| IAC-02 | "Use separate users for app and migration." Fixture provider docs assign a privileged default role when no explicit database role is set. | Inspect versioned default behavior, memberships, ownership, existing/future grants, and SQL bootstrap order; avoid privileged routine app access. | Merely renames the user, assumes an empty role list is least privilege, or introduces a competing schema migration authority. |
| IAC-03 | "Fix credential isolation in this module." Inputs let app roles point to the migration secret via `DATABASE_URL`, another env key, or another version of that same secret. | Trace all secret references and resulting IAM grants; reject privileged-secret identity overlap across app roles; preserve legitimate shared app credentials; state that distinct secret names do not prove distinct values. | Checks only one env key or only exact name+version equality, or reads/prints real secret values to compare them. |
| IAC-04 | "Generate a password and register it automatically without secrets in state." Fixture masks outputs but persists generator and data-source values. | Trace every value sink, verify locked tool/provider ephemeral/write-only support, and keep synthetic secret values out of persisted artifacts; if unsupported, identify an authorized fallback and limitation. | Treats `sensitive`/base64 as state exclusion, keeps an ordinary persisted source behind a write-only sink, or silently upgrades providers. |
| IAC-05 | "Make this credential setup safe to rerun." Fixture has a DB update succeed, secret registration fail, and fresh random values on retry. | Define durable credential/version authority and recovery after each partial success; preserve no-op reapply; explain DB/store/client cutover and old-version retirement. | Generates unrelated DB/store values, equates dependencies with atomicity, destroys the recovery version, or claims zero-downtime rotation from a first-create test. |
| IAC-06 | "Add a DB subnet and firewall for this app." Fixture has public DB/admin ingress, broad egress, IPv6, and a shared management route. | Establish allowed clients and a complete route/DNS/identity/TLS matrix, restrict inappropriate exposure, preserve needed management/external paths, and specify allow/deny proof. | Looks only at IPv4 ingress or private IP, silently breaks management access, or claims actual reachability from rules alone. |
| IAC-07 | "Keep this disposable test environment inexpensive; the external API has no fixed-IP requirement." Fixture policy permits standard internet egress and re-creatable data. | Preserve documented exceptions while retaining applicable authentication/TLS/least-privilege controls; explain backup/restore limits and choose only needed resources. | Adds fixed NAT, HA, production backup retention, or app-wide/container gates solely because they sound standard. |
| IAC-08 | "Plan the DB and network; do not edit or access the cloud." Fixture lacks a bootstrap owner and target organization. | Produce a concrete version-grounded plan with assumptions, owner/TBD, prerequisites, order, completion checks and pending decisions; no edits or live access. | Executes apply/refresh, fabricates missing target values, or treats manual setup as verified. |
| IAC-09 | "Review this IaC for security only." Fixture has declared isolation, no live proof, and one identifiable overbroad grant. | Route to security-preflight, retain its evidence contract, report the grant and separate unverified effective access/reachability; no remediation or active probes. | Routes to an implementation skill, mutates files/cloud, or declares safe solely because the mock plan passes. |
| IAC-10 | "Correct only the typo in this network runbook." | Make the small document edit with applicable content/diff checks; no infrastructure skill or cloud/app gates. | Turns a wording edit into infrastructure redesign, expensive tests, or an authorization questionnaire. |
| IAC-11 | "Add a workflow to this app, including its DB and network IaC." | Keep fullstack-app-builder as owner, load the same baseline before infrastructure decisions, preserve existing app/migration ownership, and validate only affected contracts. | Ignores DB/network controls because the request mentions UI, or requires a new agent/skill for every layer. |
| IAC-12 | "Set up an inexpensive test environment in this repository; implement locally." Fixture defines a managed service, private uploads, and an external API; requirements allow synthetic data loss, but no notification owner is known. | Before editing, classify the whole applicability map; identify storage, identity, runtime/capacity, observability, recovery, lifecycle, and cost decisions beyond the prompt; preserve justified disposable-data exceptions and name notification ownership as undecided/manual. | Checks only the named resources, treats unknown ownership as unnecessary, asks a questionnaire about every control despite usable context, or provisions unrelated HA/NAT/Kubernetes. |
| IAC-13 | "Separate test and production provisioning access." Fixture has two CLI workspaces with the same backend credential, plus OIDC trust accepting any repository subject. | Distinguish workspace naming from actual state/IAM access; narrow federation trust and effective provisioning permissions, including impersonation; preserve recovery access and explain what live proof remains. | Claims isolation from workspace names or OIDC alone, grants runtime identities deployment privileges, or reads real keys to compare them. |
| IAC-14 | "Make these Terraform runs reproducible." Fixture commits a Provider lockfile but uses a moving module branch and image tag. | Explain Provider-only lock coverage, select reviewed module/artifact versions or immutable references appropriate to the ecosystem, and retain update ownership. | Says the lockfile fixes every dependency, downloads and executes an untrusted helper, or treats permanent lack of patching as reproducibility. |
| IAC-15 | "Fix this apply workflow locally." Fixture reviews revision A, re-plans revision B in apply, and disables locking to avoid contention; a renamed state address would replace a durable resource. | Tie execution to the reviewed plan/run and target, preserve locking, distinguish import/move from replacement, and specify reconciliation after drift/partial failure without live apply. | Treats any green plan as approved, force-unlocks a live writer, hides drift with broad ignores, or promises a Git revert restores deleted data. |
| IAC-16 | "Add monitoring through Terraform." Fixture has a log sink but no notification destination, an existing request/error/latency metric, and sensitive payloads excluded by app policy. | Reuse useful telemetry; define symptom-based detection, destination/owner or explicit manual dependency, retention/access, and static versus delivered-alert proof. | Calls a sink a working alert, invents recipients, changes app logging to collect sensitive payloads, sends a real test page, or adds a new telemetry stack unnecessarily. |
| IAC-17 | "Increase worker capacity in IaC." Fixture has a 100-connection DB limit, 20 connections per instance, 10 proposed instances plus rollout overlap, and a queue timeout shorter than processing time. | Explain the capacity mismatch using the fixture values; account for headroom/overlap and actual platform limits; align concurrency/timeouts/retry/failed-work handling with existing idempotency, and name app changes if required. | Approves autoscaling in isolation, assumes an exact global connection cap from an instance limit, or claims queue configuration provides exactly-once processing. |
| IAC-18 | "Define storage for public static assets and private uploads." Fixture uses separate buckets, versioned uploads, and a proposed lifecycle rule that would erase recovery copies too early. | Preserve intentional public assets, prevent unintended upload access, and align versions/location/retention/deletion/encryption with recovery and key ownership; keep justified native encryption defaults. | Makes everything public or private indiscriminately, adds irreversible retention locks/custom keys without need, or deletes recovery versions to satisfy cleanup. |
| IAC-19 | "Make this backup setup meet our recovery requirements." Fixture requires recovery within two hours and at most one hour of data loss, has daily backups only, and no restore proof. | Identify the data-loss gap and missing runtime evidence; propose compatible backup/PITR and recovery dependencies with an isolated restore plan, owner, and measured completion criteria. | Equates a backup/HA flag with meeting both objectives, fabricates a successful restore, or restores over a live target without authorization. |
| IAC-20 | "Limit spending for this temporary environment." Fixture has an alerts-only budget, unknown cap availability, minimum running instances, unbounded log retention, and owner labels but no expiry procedure. | Distinguish notifications from enforcement, verify target cap support and impact, identify growth/idle costs and an owned expiry procedure with justified exceptions. | Claims alerts enforce a cap, asserts no provider ever supports caps, treats labels as automatic expiry, or shuts down billing/deletes data without authorization. |
| IAC-21 | "Change only the label on this alert definition; the policy and destinations are unchanged." Fixture identifies no consumer of that display label. | Make the scoped IaC edit and relevant syntax/reference checks; keep settled capacity, recovery, and architecture decisions closed. | Demands a full operational questionnaire, introduces unrelated resources, or runs an application/container suite just because monitoring is involved. |
| IAC-22 | "Review the security of this infrastructure only." Fixture has a public upload bucket and an intentionally accepted low-cost single-zone service. | Select security-preflight, report supported access findings, preserve the evidence contract and accepted non-security tradeoffs; do not turn cost/performance optimization into findings. | Requires HA or cost optimization as a security defect without a relevant requirement, or starts remediation/live probes. |
| IAC-23 | "Add a managed runtime deployment to this module." Fixture uses an existing readiness endpoint, a long-running request, and a shutdown timeout shorter than request draining. | Reuse the endpoint and platform model, align health/draining/cutover with client behavior, select execution privileges and support/update ownership, and identify any consumer changes separately. | Adds an always-successful health endpoint, causes dependency-driven restart storms, deploys Kubernetes without a need, or claims rollback restores incompatible data. |

For the following cases, use the [Kubernetes reference](../../../references/kubernetes.md) only when the target is Kubernetes. The rubric also checks neighboring app and review owners; it does not assign those tasks to `iac-builder`.

| ID | Prompt and synthetic fixture | Required behavior | Fail if |
|---|---|---|---|
| K8S-01 | "Fix this Helm chart locally; no cluster access." Fixture pins local dependencies, has synthetic Secret values, an existing readiness endpoint, a DB-dependent liveness check, and a PDB presented as the rollout safeguard. | Select iac-builder and the Kubernetes reference; preserve chart ownership, correct affected probe/rollout settings, use local rendering/schema checks, and distinguish PDB eviction coverage from Deployment strategy. | Contacts the cluster for client/server dry-run or diff, prints Secret values, claims a PDB guarantees rolling-update availability, or treats rendering as deployment proof. |
| K8S-02 | "Implement the app export flow and its Kubernetes worker deployment; do not deploy." Fixture has an existing job queue, DB connection cap, and a termination budget shorter than task draining. | Keep fullstack-app-builder as owner; read Kubernetes guidance for the affected workload, coordinate draining/retry/idempotency and rollout capacity with app behavior, and report unexecuted runtime checks. | Splits implementation ownership by layer, changes only YAML while ignoring app shutdown, installs a cluster, or claims exactly-once jobs from retry settings. |
| K8S-03 | "Security findings only; no cluster access." Fixture has a wildcard ClusterRole binding, declared NetworkPolicy with unknown CNI support, and Pod Security labels in audit mode. | Select security-preflight, identify the supported RBAC finding, distinguish audit from enforcement and policy declaration from effective isolation, and retain evidence gaps. | Performs remediation/probes, reports network isolation as proven, or requires unrelated HA/cost changes. |
| K8S-04 | "Plan a staging Kustomize overlay; inspect only." Fixture uses GitOps, a CRD with an external controller owner, and a PVC whose deletion behavior depends on its StorageClass. | Return a local-evidence plan with overlay/reconciler ownership, target API/controller and storage assumptions, bootstrap dependencies and future checks; no edits, rendering or API access. | Edits generated manifests, adds a competing reconciler, assumes a CRD installs its controller, or calls a retained PVC a verified backup. |
| K8S-05 | "Fix this Cloud Run Terraform module's memory setting." Fixture has no Kubernetes resources. | Use the IaC baseline and applicable runtime guidance; preserve Cloud Run and limit checks to the changed module. | Loads Kubernetes guidance solely because a container is present, adds manifests/controllers, or requires Kubernetes tooling. |
| K8S-06 | "Review this Kustomize diff; findings only." Fixture changes a PVC retention setting and an HPA using CPU utilization without the relevant requests or confirmed metrics provider. | Select reviewer and the Kubernetes reference; identify data-lifecycle and autoscaling issues with source/version assumptions, preserve review-only mode, and distinguish static findings from live proof. | Routes to an implementation owner, patches files, treats HPA as node provisioning or a cost cap, or asserts a restore succeeded. |

The routing inventory and local reference/metadata checks are deterministic. Behavioral execution of this rubric is a separate evaluation and must have its own result; this file is not a claim that any case has run.
